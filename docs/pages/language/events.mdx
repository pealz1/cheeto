# Events
Events are Cheeto's version of Roblox's `ReliableEvent` and `UnreliableEvent`.<br/>
They are the main way to communicate between client and server.

## Usage in Cheeto

Events can be defined using the `event` keyword.
```cheeto copy
event MyEvent {
    From: Server,
    Type: Reliable,
    Call: SingleAsync,
    Auth: "AlivePlayer",
    Data: f64
}
```

#### `From`
Determines the side from which the event is fired. <br/>
Currently Cheeto supports either `Server` or `Client`.

#### `Type`
Determines the type (reliability) of the event.
* `Reliable` - Events are guaranteed to arrive at their destination in the order they were sent in.
* `Unreliable` - Events are not guaranteed to arrive at their destination or to arrive in the order they were sent in. They also have a maximum size of 1000 bytes.

#### `Call`
Determines the listening API exposed on the receiving side.
* `SingleSync` - Events can only have one listener, but that listener cannot yield.
* `ManySync` - Events can have many listeners, but those listeners cannot yield.
* `SingleAsync` - Events can only have one listener, and that listener may yield.
* `ManyAsync` - Events can have many listeners, and those listeners may yield.
* `Polling` - Events are iterated through `Event.Iter()`.

<Callout type="error">
    Sync events should be avoided unless performance is critical.<br/>
    Yielding or erroring in sync event can cause <b>undefined and sometimes game-breaking behaviour</b>.
</Callout>

#### `Data`
Determines the data that is sent through the event, can be any [type](/language/types).<br/>
This field can be omitted if no data is required.

#### `Auth`
Names an auth rule for generated middleware. Register the rule at runtime with `Network.UseAuth(name, callback)`.
If an auth rule returns false, the incoming event is dropped before the listener runs.

```lua filename="server.luau" copy
Network.UseAuth("AlivePlayer", function(context)
    return context.Source.Character ~= nil
end)
```

<Callout type="warning">
An event naming an auth rule that was never registered has **every packet
dropped** (one warning is logged per unknown rule name). This is fail-closed by
design, and it means a typo removes a feature with no error at the call site —
register the rule in the same change that declares it. If your endpoints are
split across several generated modules, register on all of them.

Introducing `Auth` on a live game is worth doing report-only first: have the rule
record and return `true`, watch the logs, then enforce. An auth gate that depends
on a handshake winning a race against the player's first input will drop real
traffic silently.
</Callout>

#### `Honeypot`
Marks an endpoint nothing legitimate ever calls. Inbound traffic is dropped
before the payload is read and raises a violation with reason `Honeypot`.

This works because Cheeto multiplexes by `WireId` and event names never reach the
wire, so the only way to discover the endpoint is to read the generated client
module — which is what writing an exploit involves. Give it an attractive name and
never call it from game code.

```cheeto copy
event AdminSetPower {
    From: Client,
    Type: Reliable,
    Call: SingleAsync,
    Honeypot: true,
    Data: f64
}
```

Honeypots can be switched off live with `Configure({ EnableHoneypots = false })`.

#### `Idempotency`
Rejects a duplicate call rather than delivering it twice.

<Callout type="warning">
The key is the packet's sequence number, and a sequence only reaches the wire
when the sender attached a prediction id. On an event with no prediction there is
nothing identifying one logical call, so this is inert. `ReplayWindowSize` and
`ReplayStaleSeconds` have the same precondition. To bound a one-shot action that
carries no sequence, use `CooldownSeconds` — the runtime enforces that by itself
and rejects before deserialising.
</Callout>

#### `Risk` and the `Require*` fields
`Risk`, `MaxDistance`, `RequireOwnership`, `RequireTeam`, `RequireZone`,
`RequireMatch`, `RequireInventoryOwnership`, `RequireCharacterState`,
`RequireObjectHandle` and `RequireServerKnownId` are parsed and handed to your own
code in `Context.Constraints`. **The runtime enforces none of them by itself** —
they are inputs to a rule you write, and declaring one without a rule that reads
it does nothing.

Which rule depends on *what the constraint describes*:

| Constraint is about | Where to enforce it | Why |
|---|---|---|
| The **sender** (`RequireCharacterState`) | a `Policy` | Policies run before deserialisation, and the sender is already known |
| The **payload** (`MaxDistance`, `RequireOwnership`, `RequireTeam`, `RequireZone`, `RequireMatch`, `RequireInventoryOwnership`, `RequireObjectHandle`, `RequireServerKnownId`) | the `Validate` middleware | The value being constrained does not exist until after deserialisation |

`Validate` runs **after** the payload is decoded and **before** your listener, and
returning `false` drops the packet with reason `ConstraintRejected`:

```lua filename="server.luau" copy
Network.Use("Validate", function(Context)
    -- Context = { Name, Source, Channel, Size, Constraints, Payload }
    local MaxDistance = Context.Constraints.MaxDistance
    if MaxDistance and MaxDistance > 0 then
        local Target = Context.Payload[1]
        if TooFarFrom(Context.Source, Target, MaxDistance) then
            return false
        end
    end
    return true
end)
```

<Callout type="info">
The hook is emitted **only** for events that declare at least one
payload-dependent constraint. An event that declares none has a byte-for-byte
unchanged receive path — this runs on every packet, and the context table is a
per-packet allocation, so it is not paid for unless it is used.

`Risk` and `RequireCharacterState` deliberately do not trigger it: `Risk` is a
tag, and character state is knowable before decoding.
</Callout>

#### Guard Overrides
Events can override runtime guardrails:

```cheeto copy
event Attack {
    From: Client,
    Type: Reliable,
    Call: SingleAsync,
    Auth: "AlivePlayer",
    RateLimitPerSecond: 20,
    RateLimitBurst: 40,
    MaxQueuedEvents: 64,
    MaxPacketBytes: 512,
    Data: u16
}
```

##### Type Packs
Multiple data values are supported through the usage of a type pack (commonly referred to as a tuple).
Type packs can be defined as a list of [types](/language/types) seperated by a comma within parenthesis.<br/>
For example, a type pack of different [number types](/language/types#numbers) can be written like so:
```cheeto  copy
event MyTypePackEvent {
    From: Server,
    Type: Reliable,
    Call: SingleAsync,
    Data: (u8, u16, u32)
}
```

## Usage in Luau

### Firing an Event
```lua filename="client.luau" copy
cheeto.MyEvent.Fire(5)
cheeto.MyTypePackEvent.Fire(2^8 - 1, 2^16 - 1, 2^32 - 1)
```
```lua filename="server.luau" copy
cheeto.MyEvent.Fire(Player, 5)
cheeto.MyEvent.FireAll(5)
cheeto.MyEvent.FireList({Player}, 5)
cheeto.MyEvent.FireExcept(Player, 5)
cheeto.MyEvent.FireGroup("RedTeam", 5)
```

Client-origin events also expose `Predict(...)`, which sends the event and returns a local prediction id that can be passed to `cheeto.Prediction.Ack(id)` or `cheeto.Prediction.Rollback(id)`.

### Listening to an Event
```lua filename="client.luau" copy
cheeto.MyEvent.On(function(Value)
    -- ...
end)

cheeto.MyTypePackEvent.On(function(Foo, Bar, FooBar)
    -- ...
end)
```
```lua filename="server.luau" copy
cheeto.MyEvent.On(function(Player, Value)
    -- ...
end)

cheeto.MyTypePackEvent.On(function(Player, Foo, Bar, FooBar)
    -- ...
end)
```
```lua filename="disconnect.luau" copy
local Disconnect = cheeto.MyEvent.On(...)
Disconnect()
```

### Iterating an Event (Polling)
```lua filename="client.luau" copy
for Index, Value in MyEvent.Iter() do
    -- ...
end
for Index, Foo, Bar, FooBar in MyTypePackEvent.Iter() do
    -- ...
end
```
```lua filename="server.luau" copy
for Index, Player, Value in MyEvent.Iter() do
    -- ...
end
for Index, Player, Foo, Bar, FooBar in MyTypePackEvent.Iter() do
    -- ...
end
```
