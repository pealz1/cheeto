# Comparison with Zap

[Zap](https://zap.redblox.dev) is the library closest to Cheeto: both compile a schema into typed Luau modules that pack data into buffers. If you know Zap, most of Cheeto's language will look familiar.

<Callout type="info">
This page compares documented features, as of this release. Where Zap's documentation does not cover something, the table says so instead of guessing.
</Callout>

## Shared ground

Both libraries have:

- a schema language with events (`from`, `type`, `call`, `data`) and functions;
- reliable and unreliable events, with the same five call styles (`SingleSync`, `SingleAsync`, `ManySync`, `ManyAsync`, `Polling`);
- buffer serialization, batching of reliable events per frame, and a manual replication mode;
- Luau types, TypeScript definitions, output casing options, remote scoping and microprofiler labels;
- write-side type checks as an option;
- Future and Promise support for functions.

## Where they differ

| | Zap | Cheeto |
| --- | --- | --- |
| Option style | `snake_case` in the schema | `PascalCase` |
| Function yield style | One global `yield_type` | Per function, with `Yield` |
| Rate limits and cooldowns | Not documented | Per remote call and per endpoint |
| Auth rules and policies before decoding | Not documented | Yes |
| Middleware hooks | Not documented | 13 hooks, including post-decode `Validate` |
| Honeypot endpoints | Not documented | Yes |
| Kill switches | Not documented | Per endpoint and per policy group |
| Payload budgets (depth, keys, string length, NaN) | Not documented | Yes |
| Server-side movement checks, client tripwires, liveness challenges | Not documented | Optional |
| State channels with delta patches | Not documented | Yes |
| Client prediction with server acknowledgement | Not documented | Yes |
| Reliable fragmentation of large batches | Not documented | Yes |
| Version handshake and lockfile | Not documented | Yes (see [limitations](/limitations#the-handshake-does-not-block-mismatched-peers)) |
| Packet capture and replay | Tooling integration for external inspectors | Built-in capture, replay and inspector |
| Metrics | Not documented | Built-in counters |
| Option to remove `FireAll` | `disable_fire_all` | No |
| Configurable remote folder | `remote_folder` | Rotation folder only |
| Studio plugin | Not documented | Yes |

## Choosing

Zap is smaller and does one thing: fast, typed serialization. If you already validate and rate-limit in your own code and want the leanest output, it is a good choice.

Cheeto generates more code (each module includes a runtime of about 135 KB) in exchange for the protections and tooling above. It suits games where clients are actively attacked and you want those defences declared in the schema rather than rebuilt per endpoint.

## Moving from Zap

- Rename options to PascalCase: `server_output` becomes `ServerOutput`, `casing` becomes `Casing`.
- `funct` blocks become `function` blocks, with a `Yield` field instead of the global `yield_type`.
- Field names can stay lowercase: Cheeto accepts `from`, `type`, `call` and `data` as well as the capitalised forms.
- Add a `Policy` and a cooldown or rate limit to every client-sent endpoint. See the [Security model](/security/overview).
