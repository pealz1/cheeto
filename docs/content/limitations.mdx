# Limitations

This page lists what Cheeto does not do, and where its checks stop. Each entry says what happens and what to do about it. Everything here is a design limit or a property of Roblox, not a known defect.

## Security

### Clients can always see and send traffic

Anything the server sends to a client can be read by that client, and anything a client can send, an exploiter can send with any values. No networking library changes this. Validate every client request on the server with [policies](/security/policies), [constraints](/security/constraints) and your own checks, and never send secrets to clients.

### Client-side detection is best-effort

The [client shield](/security/client-shield) runs on the exploiter's machine, which they control: it can be removed, hooked or fed false results. [Client integrity](/security/client-integrity) receipts use a checksum anyone can compute from the client module. Treat both as evidence and tripwires, not proof. Keep authority on the server.

### Remote names are visible to clients

[Name rotation](/security/remote-hardening) renames the same RemoteEvent instances and publishes the current names as attributes, which is how the legitimate client module finds them. Decoys share the real remotes' name format and classes, so a generic "fire everything" tool cannot tell them apart. A script written against your game's client module can still find the real pair.

### Idempotency stops replays, not new requests

[`Idempotency`](/reference/fields#idempotency) stamps every client send with a sequence number, and the server drops a packet whose number is not newer than the last one it accepted. A captured packet sent again is dropped. A fabricated packet with a fresh number is an ordinary new request: bound those with [`CooldownSeconds`](/reference/fields#cooldownseconds), rate limits and server state.

### What the payload constraints examine

The built-in [payload constraints](/security/constraints) look at the arguments and at the fields of table arguments, one level deep:

| Constraint | Examines |
| --- | --- |
| `MaxDistance` | Every `Vector3`, `CFrame`, `BasePart`, `Model` and `Attachment`; a sender without a character is rejected when any is present |
| `RequireOwnership` | Every Instance |
| `RequireObjectHandle` | The first number |
| `RequireServerKnownId` | The first number or string |
| `RequireInventoryOwnership` | Whatever your [resolver](/reference/api/security#setinventoryresolver) checks |

Deeper values, and conditions these do not express, belong in a [`Validate` hook](/reference/api/hooks#validate).

### Dropped events without a prediction get no answer

A function call or a predicted event that the server drops is answered with the drop reason. A plain `Fire` is not answered, because nothing on the client is waiting for it. If the client needs to know, make it a function or send it with `Predict`.

## Transport

### Ids depend on cheeto.lock

Endpoints keep their ids across reorders and removals only while `cheeto.lock` is next to the schema and committed, and only in builds made with the command-line compiler: the Studio plugin does not read the lock. Without it, ids follow declaration order, as they do the first time a schema is compiled. Pin ids that must never move with [`WireId`](/reference/fields#wireid). See [cheeto.lock format](/reference/lockfile).

### Mixed schemas are not decoded

The handshake compares [schema fingerprints](/reference/options/versioning#the-schema-fingerprint), and the server stops decoding a player whose fingerprint differs from its own. There is no translation between two layouts: any change to an endpoint's id, channel or payload makes old and new builds incompatible. In Roblox both sides normally come from the same place version, so this only matters for modified clients and during updates.

### Batching adds up to a frame

Reliable events, and unreliable events with [`BatchUnreliable`](/reference/options/runtime#batchunreliable) (the default), leave at the next replication step, which runs on `Heartbeat`. [`Latest`](/reference/fields#reliabilitymode) events leave then too, keeping only the last value. Turn batching off for unreliable events that must leave immediately.

### Unreliable delivery is unreliable

Unreliable events can be lost or arrive out of order, and a lost batch loses every event in it. Use [`Sequenced`](/reference/fields#reliabilitymode) to drop out-of-order arrivals, and reliable events for anything that must arrive.

### Priority only affects shedding

[`Priority`](/reference/fields#priority) decides which events are dropped when a peer's queued bytes exceed [`MaxQueuedBytes`](/reference/options/limits#maxqueuedbytes): `Cosmetic` and `Background` go first, `Critical` and `Gameplay` never. It does not reorder a batch or change when it is sent.

### Payload checks apply to everything

The [decode budgets](/reference/options/limits#decode-budgets) apply to every endpoint in both directions. Strings over 8,192 bytes and tables over 2,048 keys are dropped by default, even when the schema allows them. Raise the budget options when a schema legitimately needs more.

### Endpoint and invoke counts

Endpoint ids are one byte with four values reserved for control frames, so a schema supports at most 252 reliable and 252 unreliable endpoints; the compiler rejects more. At most 256 invokes can be outstanding per module.

### Studio's script size limit

Studio rejects scripts over 200,000 characters. Each generated module contains the runtime (about 200 KB) unless you use [`RuntimeOutput`](/reference/options/output#runtimeoutput). Split large surfaces across several schemas with a shared runtime. See [Large schemas](/operations/large-schemas).

## Schema language

### Delta channels need a struct

A channel sends patches only when its data is a struct, because a patch names fields. Any other data type is always sent whole.

### Generic types cannot be exported

An `export` declaration cannot be generic. Export a concrete instantiation through an alias, for example `type Pair = Generic<u8, u8>`.

## Tooling

### Benchmarks run in Lune

[`--benchmark`](/reference/cli#--benchmark) and [`--load-sim`](/reference/cli#--load-sim) run the generated modules in Lune against stub remotes, with generated sample payloads and the schema's access rules removed. The byte counts are exact; the timings are Lune on your machine, which is close to but not the same as a Roblox server. Endpoints whose types have no sample (for example `DateTime`) are reported as skipped.

### TypeScript types for the runtime are structural

The generated `.d.ts` files describe every endpoint precisely. The runtime namespaces (`Security`, `Transport` and the rest) are typed from the reference, with `unknown` where a value depends on the schema. Roblox types such as `Instance` and `Vector3` come from `@rbxts/types`.
